Actively Exploited Chromium Sandbox RCE Affects All Major Browsers

A type-confusion vulnerability in V8, tracked as CVE-2026-85046, is being actively exploited in the wild and affects Chromium-based browsers prior to version 152.0.7977.82. A crafted HTML page can let a remote attacker run arbitrary code inside the browser sandbox.

Since Chrome, Edge, Brave, and most other major browsers share the Chromium engine, the flaw exposes billions of users to a credible, actively exploited attack. It highlights the fragility of relying on a single rendering engine across the web and makes urgent patching essential for both consumers and enterprises.

The bug is a type confusion in V8, Chrome's JavaScript and WebAssembly engine, and carries a CVSS score of 8.8 (High). Google fixed it in Chrome 152.0.7977.82 and reportedly paid a $1,000 bug bounty; users should also update Chromium derivatives because many browsers lag upstream releases.

hackernews · negura · Sep 5, 05:52 · Discussion · Single source

Background, discussion, and references

Market impact

The transmission channel is infrastructure-level: until patched, Chromium-based browsers are a potential entry point for stealing crypto wallet keys, recovery phrases, or DeFi session credentials. No specific asset or venue is directly implicated, so the market effect is indirect and tied to Web3 user security rather than to trading fundamentals.

Background

Browsers use sandboxing to isolate code downloaded from the internet so that a malicious page cannot compromise the rest of the operating system. RCE refers to a vulnerability that lets attackers run their own code on a victim's machine. Type confusion means the engine mistakes one JavaScript object type for another, corrupting memory in an exploitable way. V8 bugs of this kind have historically been among the most common root causes of actively exploited Chrome zero-days; a sandboxed RCE is still serious because it can be paired with a separate sandbox-escape exploit to gain full system access.

Discussion

Commenters debated the economics of the bug, noting that Google paid only $1,000 for an already exploited zero-day, and questioned why another V8 type-confusion got attention when similar bugs appear constantly. Others expressed frustration about the inherent risk of executing JavaScript/WASM from the web, joked about disconnecting entirely, and compared how quickly Brave versus GrapheneOS' Vanadium shipped fixes.

Anthropic's Claude Helps Formalize Fermat's Last Theorem in Lean

Anthropic announced that Claude, its AI system, helped produce a formally verified proof of Fermat's Last Theorem using the Lean proof assistant. The project formalized the Wiles–Taylor–Wiles argument as presented in the Darmon–Diamond–Taylor exposition, including the Langlands–Tunnell and Ribet level-lowering steps.

This is a landmark for AI-assisted mathematics, showing that Claude can help turn a famously long and intricate human proof into a machine-checkable formal proof. Anthropic argues that this speed suggests large parts of mathematics can now be formalized, which may help catch errors in existing proofs and reduce the burden on referees.

The formalization does not follow the modern proof currently being formalized by mathematician Kevin Buzzard; instead it recreates the original Wiles–Taylor–Wiles breakthrough via the Darmon–Diamond–Taylor route. Along the way, the repository develops Fontaine theory and enough of Mazur's work on the Eisenstein ideal to deal with Frey curves.

hackernews · jlebar · Sep 5, 02:42 · Discussion · Single source

Background, discussion, and references

Background

Fermat's Last Theorem states that no three positive integers a, b, and c satisfy a^n + b^n = c^n for any integer n greater than 2. Andrew Wiles proved it in 1994, with Richard Taylor helping to close a gap, but the proof is exceptionally long and advanced. Lean is an open-source proof assistant and functional programming language that lets computers check mathematical proofs line by line. Interactive tools like Lean are increasingly paired with large language models to automate or accelerate formalization, an area sometimes called AI-assisted theorem proving.

Discussion

Hacker News users responded with both enthusiasm and nuance. Mathematician Kevin Buzzard, who has been formalizing a different path to Fermat's Last Theorem, said Anthropic had beaten him to it, and pointed to his blog post for context; other commenters noted the formalization follows the older Darmon–Diamond–Taylor exposition. Some praised the result but argued the key implication for spotting errors and aiding referees should appear much earlier in the announcement, while one commenter raised concerns that Anthropic may rely on contractors hired through data vendors to formalize mathematical textbooks.

Hidden Solana v1 Upgrade Flaws Can Freeze RPC Readers and Disable Fee Limits

Solana's v1 transaction format, which raises the maximum payload from 1,232 to 4,096 bytes, can freeze RPC readers that do not opt in and can silently disable ComputeBudget-based fee limits for indexers and sponsors. The format is active on testnet and devnet but not yet activated on mainnet as of September 4.

RPC clients, indexers, relayers, and fee sponsors that fail to update could experience hard outages or enforce incorrect resource and fee limits once the first v1 transaction appears. This makes the pre-activation window a compatibility deadline for nearly all Solana infrastructure operators.

Consumers must set maxSupportedTransactionVersion: 1 for getTransaction, getBlock, and blockSubscribe, otherwise v1 requests return error -32015, whole blocks fail, and subscriptions emit null. V1 moves compute-unit and priority-fee data into a transactionConfig object, so stale indexers may report zero compute budgets; Geyser/gRPC consumers must regenerate protobuf stubs and check field 7 before reading the version flag.

Mina's Mesa hard fork halts network, invalidates zkApp verification keys

On September 3, Mina's Mesa hard fork halted transaction processing on mainnet for about eight hours, with block production pausing at roughly 15:00 UTC before the first Mesa slot at 18:00 UTC. Exchanges were instructed to suspend MINA deposits and withdrawals from the 10:00 UTC stop-transaction slot until the upgraded network became operational.

This is a high-severity protocol upgrade incident for Mina because it interrupted live transaction service, forced centralized exchanges to pause MINA transfers, and rendered deployed zkApps unable to process proof-authorized activity. It illustrates how core protocol changes, such as altered circuit constants, can directly affect application developers and users on layer-1 networks.

The upgrade halves slot time from three minutes to 90 seconds and temporarily caps zkApp transactions at 12 per block after stress tests found memory spikes when the soft limit was removed. zkApp developers must compile Mesa-compatible verification keys with o1js 3.0 and update the key stored on-chain; until then, proof-authorized activity remains paused, with no fixed migration deadline.

Mina is a layer-1 blockchain built around zero-knowledge proofs, specifically zk-SNARKs. zkApps are Mina smart contracts powered by these proofs, and developers write them in TypeScript using the o1js library.
